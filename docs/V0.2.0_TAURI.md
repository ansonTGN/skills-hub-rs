# Skills Hub Rust `v0.2.0-alpha.2` — Arquitectura Desktop Tauri

> Documento técnico de referencia para la interfaz Desktop de `skills-hub-rs`.
>
> Estado documentado: **`v0.2.0-alpha.2`**  
> Plataforma UI: **Tauri 2.11.5**  
> Toolchain de referencia: **Rust 1.96.0**  
> Repositorio: `ansonTGN/skills-hub-rs`

## 1. Objetivo

La aplicación Desktop de **Skills Hub Rust** proporciona una interfaz gráfica sobre el mismo motor Rust utilizado por la CLI.

La decisión arquitectónica principal es deliberada:

> **la GUI no reimplementa la lógica de negocio en JavaScript.**

El frontend HTML/CSS/JavaScript se limita a presentación, recogida de parámetros y llamadas IPC. La gestión de Skills, SQLite, filesystem, Git, sincronización, papelera, búsqueda y adaptadores se mantiene en el crate Rust `skills-hub-rs`.

Esto reduce divergencias entre CLI y Desktop y mantiene una única superficie de lógica privilegiada sobre filesystem y persistencia.

### Principio de separación

El frontend no accede directamente a:

- SQLite;
- repositorios Git;
- la biblioteca central;

- papelera;

## 7. Dashboard

El comando `dashboard` agrega en una sola respuesta:

- ruta raíz del hub;
- ruta de SQLite;
- Skills;
- tags;
- targets;
- herramientas conocidas;
- estado de detección;
- modo de sincronización;
- indicación `force_copy`;
- distinción builtin/custom.

Modelo conceptual:

```text
Dashboard
├── root
├── db
├── skills[]
│   ├── SkillRecord
│   ├── tags[]
│   └── targets[]
└── tools[]
    ├── key
    ├── label
    ├── global_dir
    ├── project_dir
    ├── detected
    ├── mode
    ├── force_copy
    └── builtin
```

Esto permite que el frontend pinte el estado sin consultar SQLite directamente.

## 8. Instalación

### Local

IPC:

```text
install_local(path, tags)
```

Rust construye `InstallOptions` y delega en:

```rust
hub.install_local(...)
```

El motor realiza el descubrimiento de Skills a partir de directorios que contienen `SKILL.md`.

### Git

IPC:

```text
install_git(url, revision, subdir, tags)
```

Admite:

- URL Git;
- branch/tag/revision opcional;
- subdirectorio opcional;
- tags.

La operación Git se ejecuta en el core.

## 11. Persistencia y papelera

SQLite mantiene el estado gestionado.

La GUI expone:

```text
recycle_list
recycle_restore
recycle_purge
```

La eliminación normal puede generar un snapshot recuperable que conserva información suficiente para restaurar:

- Skill;
- metadatos;
- tags;
- targets.

La política del proyecto contempla una retención lógica de 30 días antes de la purga ordinaria.

El borrado permanente se solicita explícitamente desde `remove_skill`.

## 13. Seguridad de la WebView

`v0.2.0-alpha.2` introduce una Content Security Policy restrictiva.

Configuración efectiva:

```text
default-src     'self'
connect-src     ipc: http://ipc.localhost
script-src      'self'
style-src       'self'
img-src         'self' data:
font-src        'self'
object-src      'none'
base-uri        'none'
form-action     'none'
frame-src       'none'
frame-ancestors 'none'
```

Headers adicionales:

```text
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

### Consecuencias

El modelo reduce la superficie de:

- carga remota de scripts;
- ejecución de contenido externo;
- plugins/objetos;
- embedding en frames;
- formularios externos;
- acceso innecesario a cámara, micrófono o geolocalización.

La UI actual utiliza assets locales, por lo que esta CSP es compatible con el diseño de `alpha.2`.

---

## 14. Límites del modelo de seguridad

La CSP protege principalmente la superficie WebView.

No sustituye los controles del core sobre:

- filesystem;
- rutas;
- symlinks;
- junctions;
- overwrite;
- Git;
- persistencia;
- borrado.

Por eso el diseño mantiene esas decisiones en Rust y no en JavaScript.

Principios del core relevantes para Desktop:

- rechazo de origen/destino solapados;
- no sobrescritura sin autorización explícita;
- eliminación segura de enlaces;
- preservación del origen local;
- protección de targets compartidos;
- staging previo en actualizaciones locales;
- actualización Git mediante repositorio temporal.

### Riesgos principales

| Riesgo | Control actual |
| --- | --- |
| Script remoto en UI | CSP `script-src 'self'` |
| Embedding/framing | `frame-ancestors 'none'` |
| Navegación de formularios | `form-action 'none'` |
| MIME confusion | `nosniff` |
| Acceso a sensores | `Permissions-Policy` |
| Sobrescritura accidental | `overwrite` explícito |
| Borrado irreversible accidental | papelera |
| Solapamiento origen/destino | validación core |
| Dependencia vulnerable | RustSec audit |
| Artefacto alterado | SHA-256 + attestation |

## 16. Operaciones síncronas y responsividad

En `alpha.2`, los handlers Tauri están implementados como funciones Rust síncronas:

```rust
#[tauri::command]
fn install_git(...) -> Result<...> { ... }
```

Esto es simple y correcto funcionalmente, pero operaciones como:

- clonación Git;
- actualización Git;
- scan de filesystem;
- copias grandes;
- hashing;
- actualización global;

pueden consumir tiempo apreciable.

### Objetivo para `alpha.3`

Separar operaciones potencialmente bloqueantes mediante una estrategia como:

```text
async command
    │
    ▼
spawn_blocking / worker
    │
    ▼
SkillsHub operation
```

La meta no es cambiar el core, sino mantener predecible la capacidad de respuesta del runtime y habilitar posteriormente:

- progreso;
- cancelación;
- estados `busy`;
- errores por operación;
- feedback incremental.

## 30. Limitaciones deliberadas de `alpha.2`

Todavía no se consideran cerrados para una versión estable:

- selector gráfico nativo de rutas;
- ejecución asíncrona/progreso de operaciones Git y filesystem;
- cancelación de operaciones;
- updater automático;
- firma de código comercial/OS-level;
- smoke testing profundo de instalación/desinstalación;
- SBOM de artefacto final que incluya componentes nativos;
- UX de resolución avanzada de errores/conflictos.

Estas limitaciones no invalidan el motor actual; definen el trabajo restante antes de promover `0.2.0` a estable.

## 34. Resumen arquitectónico

`skills-hub-rs-desktop` debe entenderse como una **capa de interacción** sobre el motor Rust, no como una aplicación independiente con un segundo modelo de dominio.

La dirección de evolución recomendada es conservar esa propiedad:

```text
UI cada vez mejor
      │
      ▼
IPC más explícito
      │
      ▼
mismo core Rust
      │
      ▼
mismas invariantes
```

Esto permite que CLI y Desktop evolucionen sin duplicar reglas críticas de seguridad, sincronización y persistencia.
